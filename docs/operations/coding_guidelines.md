# 开发与代码规范指引

为保证 Nova 各组件可模块化扩展、易维护且低耦合，开发时需遵循以下统一规范。

## 通用原则

- **分层清晰**：严格区分表现层、应用服务层、领域逻辑层、数据访问层。禁止跨层直接调用非暴露接口。
- **模块化设计**：每个功能模块（认证、执行、计费等）暴露明确定义的接口/服务，内部实现可替换；共用逻辑抽取为共享库。
- **依赖倒置**：核心业务不依赖具体实现，使用接口或抽象类注入，便于测试与替换。
- **低耦合高内聚**：模块之间仅通过契约（API、事件）交互；避免循环依赖与跨模块数据结构泄漏。
- **可拓展性**：预留策略模式、配置化扩展点。新脚本、支付方式等控制在各自模块内扩展。
- **配置优先**：环境差异通过配置或依赖注入处理，严禁在代码中写死路径、地址、凭据。
- **错误处理**：统一错误码与异常类型；捕获后转换为约定的响应/事件，并记录可追踪的日志。
- **日志与追踪**：所有关键操作写入结构化日志，携带 `traceId`、`tenantId`、`pcId` 等；敏感信息需脱敏。
- **测试**：核心逻辑需具备单元测试；跨模块流程提供集成测试（可使用模拟器/Mock 服务）。
- **文档先行**：需求变更先更新 `docs/` 文档，再开始编码，确保团队共识。

## NovaServer（Python/FastAPI）

- 使用 `routers/` 目录拆分模块，依赖注入通过 `Depends` 管理。
- Pydantic 模型与 SQLAlchemy ORM 分离，禁止直接返回 ORM 实体。
- 服务层（`services/`）仅暴露接口函数，内部可使用 Repository 或外部 API。
- 异步优先：REST/WS handler 使用 `async def`，数据库操作使用异步驱动。
- 配置使用 `pydantic-settings` 或 `.env`，注入到应用上下文。
- 统一响应包装，错误通过自定义异常 + 全局异常处理器实现。
- Background tasks 独立于业务逻辑模块，定时任务配置集中管理。

## NovaDesk（Flutter）

- 遵循 MVVM/BLoC 等统一状态管理模式，禁止在 Widget 中直接访问网络或数据库。
- 使用 `data`、`domain`、`presentation`、`platform` 四层组织代码；平台相关服务（ADB、文件系统）通过抽象类 + DI 提供。
- 网络层统一使用 dio 封装；WebSocket 封装为 Service，事件分发通过 Stream/StateNotifier。
- 模板、本地存储采取 Repository 模式，便于替换存储实现。
- UI 组件保持无副作用，可重复使用；页面逻辑通过 ViewModel 处理。
- 编码规范遵循 Dart 官方风格，使用 `dart format` + `lint`。

## NovaAgent（Android/Kotlin）

- 模块分层：`core`（配置、WS、依赖注入）、`execution`（状态机、Runner）、`scripts`（脚本实现）、`reporting`（回报）。
- 使用依赖注入（如 Koin/Hilt）管理单例；脚本通过注册表模式注入。
- 严禁脚本直接访问低层 WebSocket，需通过 `ExecutionContext` 与 `Reporter`。
- 操作 UiAutomator、OpenCV、IME 等能力需包裹在特定模块，脚本仅调用接口。
- 所有网络操作使用挂起函数，配合协程管理生命周期；注意处理超时与重试。
- 临时文件、附件下载放置在指定目录，执行结束后清理。
- 代码遵循 Kotlin 官方编码规范，开启 `ktlint`/`detekt` 等静态检查。

## 协同与审查

- 每个模块提交前需自检：代码格式、lint、单元测试。
- 重大改动必须更新文档与变更日志，并由相关组件负责人 Code Review。
- 发布分支需通过自动化流水线验证（编译、测试、打包）。
- 跨团队接口变更必须提早同步并提供向后兼容方案（版本字段、灰度开关等）。

遵循以上规范，确保系统在功能扩展与长期维护中保持稳定、可预测的架构质量。

## 协作流程与 To-Do 管理

- **开发前确认文档**：所有任务开始前先阅读 `docs/` 中对应章节，若需求/接口描述不足须先补齐文档再动手。
- **任务列表**：各组件团队维护可追踪的 To-Do（可在项目管理工具或仓库 issue 中），任务完成需更新状态并在备注中关联文档段落与提交记录。
- **文档先于代码**：任何接口、协议、数据模型、流程调整，必须先修改 `docs/` 中的相关文档，通过评审后才允许提交代码实现。
- **规范执行**：代码提交必须符合本指南，包括分层、依赖倒置、日志、测试、格式化等要求；提交前务必运行 lint/测试。
- **Git 提交流程**：文档或代码变更完成后执行 `git add` / `git commit`，推荐采用语义化提交信息（如 `docs:`、`feat:`、`fix:`），再通过 `git push` 推送到远端仓库；重要改动需通过 PR 审查。
- **跨团队同步**：涉及其他组件的改动（如消息字段新增）需在公共渠道同步，并注明已更新文档的位置，保证并行会话无缝衔接。
