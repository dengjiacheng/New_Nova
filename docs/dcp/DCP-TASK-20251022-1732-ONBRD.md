# 摘要

全面接手 Nova 平台项目，建立权威文档、架构说明、跨端依赖清单，补齐测试基线（覆盖率 ≥ 75%），并形成治理路线与风险矩阵，确保多端协同与持续交付稳定性。

## 背景

- 代码仓包含三大模块：Android 端 `NovaAgent`、Flutter 桌面端 `NovaDesk`、FastAPI 云端 `NovaServer`，尚缺少统一文档与治理流程。
- 现有文档与依赖列表零散，测试覆盖率与指标未知，缺乏统一的质量与安全基线。

## 目标与交付物

1. 产出权威项目总览文档，涵盖架构、模块职责、数据/控制流。
2. 汇总三端依赖清单（运行时、开发、工具链），标注关键版本与兼容性约束。
3. 构建覆盖率 ≥ 75% 的测试基线，并输出运行脚本、指标记录与补测计划。
4. 给出治理路线（季度/迭代关注点、指标体系）及风险矩阵（含缓解措施）。
5. 组织关键事实沉淀至 `docs/reference/`，建立后续维护机制。

## 工作拆解

- 文档专项：梳理现状、形成项目总览、架构说明、依赖清单、治理路线、风险矩阵。
- 测试专项：盘点现有测试、补齐缺口、统一覆盖率统计脚本并留存指标。
- 自动化与守护：确认守护流程、更新 DCP 与参考文档，支撑后续自动 PR。

## 里程碑

- M1：完成现状审计与交付范围确认。
- M2：落地文档体系与依赖清单。
- M3：测试覆盖率 ≥ 75%，形成基线报告及补测脚本。
- M4：输出治理路线、风险矩阵并完成知识库固化。

## 风险与应对

| 风险 | 影响 | 缓解措施 |
| ---- | ---- | -------- |
| 模块跨语言导致知识割裂 | 影响延续性 | 文档统一结构+责任人映射，定期审查 |
| 测试依赖环境复杂 | 覆盖率难达标 | 分模块独立跑，提供离线 Mock 与容器配置 |
| 依赖升级兼容性未知 | 引发回归 | 引入依赖监控清单与季度升级窗口 |
| 守护/CI 与本地流程背离 | 自动化失效 | 统一脚本入口、定期演练守护流程 |

## 验收标准

- 文档存放于 `docs/reference/` 且被守护纳入权威目录。
- 测试覆盖率报告 ≥ 75%，并记录于 `docs/reference/testing/coverage.md`。
- 治理路线与风险矩阵形成可执行事项，附后续跟踪机制。
